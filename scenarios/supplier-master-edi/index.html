Le fichier fournisseurs part à l'EDI en ASCII avec un identifiant stable

Objectif Envoyer à l'EDI des fournisseurs au format qu'il impose, avec un identifiant qui ne change pas.

La plateforme EDI des achats impose des noms en ASCII, en majuscules, de 35 caractères au plus, et un identifiant par fournisseur. L'export de l'ERP a des accents, de longues raisons sociales, des inactifs, et des identifiants N/A, 0 ou vides.

  • les noms mis au format de l'EDI;
  • N/A et 0 vidés et comptés, un identifiant manquant dérivé du code;
  • le lendemain, les mêmes identifiants.

Le fichier mis au format EDI, les identifiants laissés tels quels

filter-where garde les actifs. Les noms passent en ASCII, en majuscules, coupés à 35. to-uuid avec on-invalid: keep laisse les identifiants tels quels, pour les regarder.

  • IN 8, OUT 6: deux inactifs écartés
  • N/A et 0 encore là

    35 caractères

    F0001 et F0005 ont le même nom une fois coupés.

Ce que prouve cette étape

8 = 6 + 2: les deux inactifs sont écartés et comptés. La contrainte de l'EDI se voit sur chaque ligne.

manifests/10-suppliers.yaml
apiVersion: connectors.lumnik.io/v1kind: Connectormetadata:  name: scenario-suppliers-b  connector_type: csv-file  scopes: [purchasing-b]spec:  transport:    kind: local    path: /tmp/lumnik-scenario/supplier-master-edi/b/suppliers.csv  parser:    delimiter: ";"  after_process: none  mapping:    dataset:      - filter-where: { column: ACTIF, equals: "O" }        # inactive suppliers out, counted    row:      - map-columns:          rename: { FOURN_CODE: code, FOURN_NOM: name, ACTIF: active, EXT_ID: ext_id, PAYS: country }      - defaults: { country: FR }                            # an empty country is France    cell:      - remove-diacritics: { columns: [name] }               # Électricité -> Electricite      - upper: { columns: [name] }      - regex-replace: { column: name, pattern: "&", replacement: " ET " }      - regex-replace: { column: name, pattern: "[^A-Z0-9 ]", replacement: " " }   # what the EDI refuses      - regex-replace: { column: name, pattern: " +", replacement: " " }      - clean: { columns: [name], strip: true }      - truncate: { column: name, length: 35 }               # the EDI's hard limit      - to-uuid: { column: ext_id, on-invalid: keep }        # look first: N/A and 0 left as they came

Ce que prouve cette étape

Un identifiant inventé est déclaré par son nom, et compté quand il remplace une valeur reçue.

manifests/11-suppliers-policy.yaml
apiVersion: connectors.lumnik.io/v1kind: Connectormetadata:  name: scenario-suppliers-b  connector_type: csv-file  scopes: [purchasing-b]spec:  transport:    kind: local    path: /tmp/lumnik-scenario/supplier-master-edi/b/suppliers.csv  parser:    delimiter: ";"  after_process: none  mapping:    dataset:      - filter-where: { column: ACTIF, equals: "O" }        # inactive suppliers out, counted    row:      - map-columns:          rename: { FOURN_CODE: code, FOURN_NOM: name, ACTIF: active, EXT_ID: ext_id, PAYS: country }      - defaults: { country: FR }                            # an empty country is France    cell:      - remove-diacritics: { columns: [name] }               # Électricité -> Electricite      - upper: { columns: [name] }      - regex-replace: { column: name, pattern: "&", replacement: " ET " }      - regex-replace: { column: name, pattern: "[^A-Z0-9 ]", replacement: " " }   # what the EDI refuses      - regex-replace: { column: name, pattern: " +", replacement: " " }      - clean: { columns: [name], strip: true }      - truncate: { column: name, length: 35 }               # the EDI's hard limit      - to-uuid: { column: ext_id, on-invalid: "null", generate-from: code }   # junk emptied, counted; an empty id derived from the code

Limites

  • truncate coupe sans prévenir: F0001 et F0005 portent le même nom à 35 caractères, seuls leurs codes les distinguent.
  • Un identifiant dérivé ne se joint à aucun autre système.
  • Fournisseurs synthétiques.

Achats · EDI

Les fournisseurs partent à l'EDI.

Chaque nuit, depuis l'ERP.

Huit fournisseurs, six actifs

Le problème

L'EDI impose sa forme.

  • ASCII, majuscules, 35 caractères.
  • Un identifiant par fournisseur.

Ce qui n'est pas modifié

L'ERP reste tel quel.

  • Son export, avec ses accents.
  • Aucune correction à la source.

Le piège

Des identifiants qui n'en sont pas.

  • N/A, 0, ou rien du tout.
  • Un identifiant au hasard change chaque nuit.

Ce qu'il a fallu écrire

to-uuid: { generate-from: code }

Une ligne.

  • Le même code donne le même identifiant.
  • Les valeurs fausses sont vidées et comptées.
  • Deux manifestes, 43 lignes.

Le lendemain

Les mêmes identifiants.

  • Un fournisseur de plus reçoit le sien.
  • Aucune ligne retirée.

La limite

Couper à 35 peut confondre deux noms.

  • Seuls leurs codes les distinguent.
