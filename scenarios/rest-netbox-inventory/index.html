NetBox, l'inventaire réseau: on nomme Django REST, on dit Token, tout est lu.

Objectif Lire chaque nuit tous les équipements d'un NetBox, la référence de l'équipe réseau, avec un jeton en lecture seule.

NetBox est bâti sur Django REST Framework: count, next et results dans chaque réponse, et un jeton présenté par le mot Token, pas Bearer. lumnik nomme les deux:

  • pagination: { kind: drf-limit-offset }: 120 équipements en 3 requêtes;
  • auth: { kind: bearer, scheme: Token }: le mot que NetBox attend;
  • la nuit suivante, les 6 switchs passés hors ligne sont dans le hub.

Un vrai NetBox: 3 sites, 120 équipements

NetBox v4.1 avec PostgreSQL et Valkey, comme le projet netbox-docker. 3 sites, 120 switchs et routeurs, actifs, planifiés ou hors ligne. L'API répond à la manière de Django REST Framework:

  • count: le nombre d'équipements
  • next: l'URL de la page suivante
  • results: les équipements
  1. 1
    Le jeton

    Un jeton en lecture seule, présenté par « Authorization: Token <clé> ». « Bearer » est refusé (403).

Ce que prouve cette étape

NetBox pagine et s'authentifie à la manière de Django REST Framework.

120 équipements, 3 requêtes

Un connecteur rest-generic.

  • auth: bearer, scheme: Token: le mot que NetBox attend devant la clé
  • pagination: drf-limit-offset: offset et limit, count comme total
  • headers: Accept: application/json
  1. 1
    Trouvé en route

    Le hub n'écrivait que « Bearer »: la clé scheme vient d'icreated/lumnik#1640.

Ce que prouve cette étape

Le preset et le mot du framework suffisent.

manifests/10-devices.yaml
apiVersion: connectors.lumnik.io/v1kind: Connectormetadata:  name: scenario-netbox-a  connector_type: rest-generic  scopes: [network]spec:  base_url: http://host.docker.internal:9270/api  auth: { kind: bearer, scheme: Token, token_env: SCENARIO_NETBOX_TOKEN }   # Django REST Framework's token word  headers:    - { name: Accept, value: application/json }  endpoints:    - id: devices      path: /dcim/devices/      method: GET      pagination: { kind: drf-limit-offset, limit: 50 }      # NetBox is Django REST Framework      target:        kind: hybrid        table: ext.scenario_netbox_a        unique_key: $.id        promote:          - { name: name, path: $.name, type: text }          - { name: site, path: $.site.slug, type: text }          - { name: status, path: $.status.value, type: text }          - { name: model, path: $.device_type.model, type: text }          - { name: last_updated, path: $.last_updated, type: timestamptz }

Limites

  • Chaque nuit relit tout l'inventaire. Le filtre last_updated de NetBox permettrait de ne relire que les changements; ce rejeu ne le montre pas, son inventaire étant créé dans la minute.
  • Un équipement supprimé de NetBox reste dans le hub avec son dernier état.
  • NetBox de démonstration, équipements synthétiques.

NetBox de démonstration

Le problème

NetBox refuse le jeton tel qu'on l'envoie d'habitude.

  • Il attend « Token <clé> », pas « Bearer <clé> ».
  • C'est la règle de Django REST Framework, sur lequel il est bâti.

Ce qui n'est pas modifié

NetBox reste tel quel.

  • Un jeton en lecture seule.
  • Son API REST standard.

Ce qu'il a fallu écrire

auth: { kind: bearer, scheme: Token }
pagination: { kind: drf-limit-offset }

On nomme le framework et son mot.

Un connecteur de 28 lignes.

Le rouge

Le rejeu a trouvé un manque.

  • Le hub n'écrivait que « Bearer ».
  • Il fallait ranger « Token » dans le secret: corrigé (icreated/lumnik#1640).

Le vert

120 équipements, 3 requêtes.

  • La nuit suivante, 6 switchs passés hors ligne.
  • Le hub les compte par site.

La limite

Chaque nuit relit tout l'inventaire.

  • Le filtre last_updated de NetBox permettrait de ne relire que les changements.
  • Un équipement supprimé reste dans le hub, avec son dernier état.
