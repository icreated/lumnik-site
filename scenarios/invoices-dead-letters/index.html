Une facture au montant illisible attend sa correction à la source

Objectif Ne jamais écrire une facture sans montant, et suivre chaque ligne écartée jusqu'à sa correction.

Un export de factures fournisseurs porte deux montants mal saisis et une facture de test.

  • les trois mises de côté, telles qu'elles ont été lues;
  • la facture de test écartée;
  • les deux autres corrigées à la source, et leur lettre fermée par la bonne lecture.

Ce que prouve cette étape

Une valeur illisible n'est pas écrite vide: la ligne est mise de côté, et lu = écrit + écarté.

manifests/10-invoices.yaml
apiVersion: connectors.lumnik.io/v1kind: Connectormetadata:  name: scenario-invoices-b  connector_type: csv-file  scopes: [invoices-b]spec:  transport:    kind: local    path: /tmp/lumnik-scenario/invoices-dead-letters/b/invoices.csv  parser:    has_header: true  after_process: none  mapping:    on-error:      fields: { amount_eur: dlq }   # an unreadable amount: the invoice goes to the dead letters    row:      - validate-row: { required: [invoice_no, supplier_id] }    cell:      - parse-date: { column: invoice_date, formats: ["yyyy-MM-dd"] }      - parse-number: { column: amount_eur, decimal-separator: "." }

Limites

  • on-error s'applique aux connecteurs CSV ; dlq est refusé à côté de split-row.
  • Le hub vérifie que la lecture nommée a pu porter la ligne (même connecteur, terminée, postérieure), pas qu'elle l'a écrite.
  • Factures synthétiques.

Le problème

Des montants illisibles.

  • 1.250.00

Ce qui n'est pas modifié

L'ERP reste la référence.

  • La correction se fait à la source.
  • Rien n'est retouché dans le hub.

Le piège

Une facture écrite sans montant.

  • Elle passe dans les totaux.
  • Rien ne la signale.

Ce qu'il a fallu écrire

on-error: { fields: { amount_eur: dlq } }

Une ligne.

  • La facture attend, avec sa ligne lue.
  • Rien ne disparaît en route.
  • Deux manifestes, 45 lignes.

  • Plus aucune lettre ouverte.

La limite

Pour les connecteurs CSV.
