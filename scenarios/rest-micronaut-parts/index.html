Micronaut: les pièces du magasin lues en trois requêtes

Objectif Lire toutes les pièces détachées d'un service Micronaut par son API, même quand le magasin y travaille.

Un vrai Micronaut 4.7 et 130 pièces fictives, rendues par la Page du repository.

  • cinquante par page: les 130 en trois requêtes, le total vérifié;
  • une pièce supprimée pendant la lecture: le total bouge, la liste est relue, rien n'est perdu.

130 pièces derrière une Page

Un contrôleur Micronaut 4.7 rend la Page de Micronaut Data JDBC telle quelle, sur H2 en mémoire. Le journal d'accès de Netty montre chaque requête reçue.

  • totalSize: 130
  • totalPages: absent

Les 130 pièces en trois requêtes

pagination: { kind: micronaut, size: 50 }. Le hub demande ?page=0&size=50, lit content et compare les lignes lues à totalSize.

  • size: la taille de page demandée
  • arrêt dès que les lignes lues atteignent totalSize (#1800)
  • 130 sur 130
  1. 1
    Avant la correction

    Le preset attendait totalPages, que Micronaut 4 n'envoie pas: chaque run demandait une page vide de plus.

Ce que prouve cette étape

Une ligne suffit pour lire une Page de Micronaut.

manifests/10-parts.yaml
apiVersion: connectors.lumnik.io/v1kind: Connectormetadata:  name: scenario-micronaut-a  connector_type: rest-generic  scopes: [magasin]spec:  base_url: http://host.docker.internal:9380  endpoints:    - id: parts      path: /parts      method: GET      pagination: { kind: micronaut, size: 50 }        # ?page=0&size=50, reads $.content, checks $.totalSize      target:        kind: hybrid        table: ext.scenario_micronaut_a        unique_key: $.ref        promote:          - { name: label, path: $.label, type: text }          - { name: supplier, path: $.supplier, type: text }          - { name: stock, path: $.stock, type: integer }

Une pièce supprimée: la liste est relue

Dix par page, une requête par seconde. Pendant la lecture, on supprime PCE-0001, déjà lue en page 0. Les pièces suivantes remontent d'une place. totalSize passe de 130 à 129: le hub relit la liste depuis la page 0 (#1796).

  • default_rate_limit: une requête par seconde
  • IN 189: la première lecture, puis la relecture
  • les 129 restantes sont toutes dans la table

Limites

  • Micronaut sert au plus 100 lignes par page: une size plus grande est réduite sans le dire. Déclarer une size de 100 ou moins.
  • Une pièce supprimée reste dans la table du hub: une lecture complète ajoute et met à jour, elle n'efface pas.
  • La relecture compte deux fois les lignes lues deux fois dans IN; l'upsert n'en garde qu'une.
  • 130 pièces fictives, écrites au démarrage du service.

Magasin · pièces

Les pièces sont dans un service Micronaut.

Il faut toutes les lire, par son API.

Micronaut 4.7, 130 pièces

Le problème

L'API rend la liste par pages.

  • Une Page de Micronaut Data.
  • Le magasin travaille pendant la lecture.

Ce qui n'est pas modifié

Le service reste tel quel.

  • Son contrôleur rend la Page telle quelle.
  • Aucun module, aucun réglage.

Le piège

Micronaut 4 ne donne pas le nombre de pages.

  • Chaque page porte totalSize: 130.
  • totalPages est absent.

Ce qu'il a fallu écrire

pagination: { kind: micronaut, size: 50 }

Une ligne.

  • Le hub s'arrête quand il a lu totalSize.
  • Trois requêtes pour 130 pièces.
  • Un connecteur de 22 lignes.

Pendant la lecture

Une pièce supprimée: la liste est relue.

  • Le total passe de 130 à 129.
  • Les 129 restantes sont toutes là.

Ce qui a été corrigé

Deux trous trouvés, deux corrections.

  • Le total vérifié sur chaque page (#1796).
  • Plus de page vide en fin de lecture (#1800).
