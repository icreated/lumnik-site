Deux plans diffusés qui perdent leur PDF pendant la nuit

Objectif Lire le registre des plans d'un PLM sur Oracle sans lire les plans eux-mêmes, et savoir le matin même qu'un plan diffusé a perdu son fichier.

Un bureau d'études garde ses plans dans un PLM sur Oracle: une ligne par révision, le PDF dans un BLOB.

  • le hub ne lit pas un BLOB: la table est refusée telle quelle, colonne nommée;
  • l'administrateur ajoute une vue sans le plan, sa taille en octets à la place;
  • cette nuit, la migration de l'archivage recopie deux révisions diffusées sans leur PDF: deux décisions.

Le registre des plans, sur Oracle 23ai

Treize révisions de huit plans. Chaque ligne porte son PDF.

  • CONTENT BLOB: le plan lui-même, de 614 à 625 octets ici
  • DESCRIPTION CLOB: ce qui change d'une révision à l'autre
  • MODIFIED_AT: le PLM l'écrit à chaque modification
  • un compte HUB_READER, en lecture seule
  1. 1
    Le brouillon

    PL-1008 A est en cours de dessin: pas encore de fichier, 0 octet. Ce n'est pas une perte.

La table telle quelle: refusée, colonne nommée

Le fournisseur Oracle lit les scalaires et les CLOB, pas un BLOB.

  • discover liste CONTENT BLOB sous UNSUPPORTED
  • add refuse la table et dit pourquoi
  • ROWS -1: Oracle n'a pas encore de statistiques sur la table
  1. 1
    Une limite, pas une panne

    Le hub ne fait pas semblant de lire le BLOB. Il dit lequel, avant le premier run.

Ce que prouve cette étape

Une vue sans le plan, sa taille à la place

L'administrateur Oracle ajoute une vue et la donne à HUB_READER.

  • DBMS_LOB.GETLENGTH(CONTENT): la taille du PDF, en octets
  • RTRIM(REV): sans le blanc de remplissage du CHAR(2)
  • discover --include-views la liste: UNSUPPORTED vide, PK vide (une vue n'en a pas)
  1. 1
    Pesé, pas lu

    Les octets du PDF ne traversent jamais le hub. Seule sa taille sort d'Oracle.

Ce que prouve cette étape

Le geste qui contourne un BLOB se vérifie avant d'écrire le manifeste.

Treize révisions, la taille de chaque fichier

Le connecteur jdbc-generic lit la vue.

  • mode: watermark sur MODIFIED_AT: une ligne modifiée sera relue
  • pk_columns: [ID], déclaré, puisque la vue n'a pas de clé
  • rename: les noms d'Oracle en minuscules dans le hub
  1. 1
    Pourquoi pas full

    En mode full, le hub reprend après la dernière clé lue: une ligne modifiée sur place n'est jamais relue. La perte de cette nuit serait passée inaperçue.

Un plan diffusé dont le fichier est vide

Le Process écoute la table du connecteur.

  • status=RELEASED: un brouillon sans fichier est normal
  • content_bytes=0: le PDF est vide
  • key: doc_no, la décision porte le numéro du plan
  1. 1
    Le brouillon n'est pas compté

    PL-1008 A est à 0 octet depuis le premier run: sans status=RELEASED, la règle le signalerait chaque nuit.

Ce que prouve cette étape

Une règle d'un bureau d'études s'écrit en deux conditions.

manifests/20-file-lost.yaml
apiVersion: apps.lumnik.io/v1kind: Processmetadata:  name: scenario-plm-file-lost-aspec:  scope: engineering-a  on: { event: data.row.changed, table: connector.t_scenario_plm_drawings_a }  when:    - "status=RELEASED"    - "content_bytes=0"                # a released drawing whose PDF is empty  emit:    type: decision.drawing-file-lost-a    message: "{doc_no} rev {rev} ({title}) is released since {released_at} and its file {file_name} is empty — find the PDF before the workshop asks for it"    key: doc_no

La migration de l'archivage perd deux PDF

Les PDF partent vers le nouveau stockage documentaire. Deux n'arrivent pas, et leurs lignes reviennent avec un BLOB vide.

  • le PLM met MODIFIED_AT à jour: le run suivant relit ces deux lignes, IN 2
  • PL-1004 C et PL-1007 B sont diffusés, à 0 octet: deux décisions
  • PL-1008 A, le brouillon, reste à 0 octet sans décision
  1. 1
    Le message

    Plan, révision, titre, date de diffusion, nom du fichier: de quoi le retrouver avant que l'atelier ne le demande.

Limites

  • Le hub ne lit pas un BLOB: ni le PDF, ni son contenu, ni une empreinte. Une vue en donne la taille; un PDF corrompu mais non vide passe.
  • La vue est un geste de l'administrateur Oracle: le hub ne la crée pas.
  • Le mode watermark suppose que le PLM met MODIFIED_AT à jour. Une écriture qui ne le touche pas n'est pas relue.
  • La règle ne voit que les pertes à venir: un plan déjà vide au premier run est lu avant que le Process existe.
  • Joué sur Oracle 23ai Free. lumnik Pro seulement: l'édition Open n'a pas de fournisseur Oracle.
  • Plans, révisions et dates synthétiques; les PDF sont de vrais PDF d'une page.

Les plans vivent dans Oracle.

Une ligne par révision, le PDF dans un BLOB.

CONTENT BLOB

Le problème

Le hub ne lit pas un BLOB.

  • La table est refusée, colonne nommée.
  • Et un PDF vide ne se voit nulle part.

Ce qui n'est pas modifié

La table du PLM reste telle quelle.

  • Le PLM continue d'écrire ses plans.
  • Aucun PDF ne quitte Oracle.

Ce qu'il a fallu écrire

NVL(DBMS_LOB.GETLENGTH(CONTENT), 0)
  AS CONTENT_BYTES

Une vue: le plan pesé, pas lu.

  • mode: watermark sur MODIFIED_AT.
  • Une règle: diffusé et 0 octet.

Ce qui a été corrigé

discover --include-views montre la vue (#1890).

  • ROWS -1 pour une table jamais analysée (#1891).
  • PL-1004 C et PL-1007 B: deux décisions.
