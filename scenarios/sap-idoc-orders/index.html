SAP ORDERS05: un IDoc où l'article ne porte pas sa commande

Objectif Lire chaque ligne de commande d'un IDoc SAP avec son article, sa quantité et son numéro de commande, sans reprendre celui de l'IDoc précédent.

Le SAP d'un client écrit ses commandes en IDocs ORDERS05, dans un fichier à plat. La commande est en tête de l'IDoc, l'article plus bas.

  • seize enregistrements découpés à leur position;
  • chaque ligne avec sa commande, sa quantité et son unité;
  • un IDoc sans commande ne prend pas celle du précédent.

Des enregistrements à largeur fixe, découpés par position

lines: true lit un enregistrement par ligne. Des regex-extract découpent les champs à leur position.

  • 16 enregistrements
  • 120.000 lu 120
  1. 1
    120.000

    Lu avec decimal-separator ".".

Ce que prouve cette étape

Un IDoc à plat se lit sans middleware.

manifests/10-idoc.yaml
apiVersion: connectors.lumnik.io/v1kind: Connectormetadata:  name: scenario-idoc-b  connector_type: csv-file  scopes: [order-desk-b]spec:  transport:    kind: local    path: /tmp/lumnik-scenario/sap-idoc-orders/b/*.txt   # the customer's SAP writes ORDERS05 IDocs as flat files  parser:    lines: true                    # one record per line, fixed width, no separator  after_process: none  mapping:    cell:      - regex-extract: { column: line, required: true, pattern: "^(\\S+)", groups: { 1: segment } }   # EDI_DC40 or E2…      - regex-extract:             # DOCNUM after TABNAM + MANDT (control record) or SEGNAM + MANDT (data record), then SEGNUM;          column: line             # one pattern for both: a second regex-extract would write null where it misses          pattern: "^(?:EDI_DC40.{5}|E2.{31})(\\d{16})(\\d{6})?"          groups: { 1: docnum, 2: segnum }      - regex-extract: { column: line, pattern: "^E2EDK02 {23}.{33}001(.{35})", groups: { 1: po_number } }   # the buyer's PO      - regex-extract:             # an item: POSEX, then MENGE and MENEE          column: line          pattern: "^E2EDP01 {23}.{33}(.{6}).{5}(.{15})(.{3})"          groups: { 1: item, 2: quantity, 3: unit }      - regex-extract: { column: line, pattern: "^E2EDP19 {23}.{33}(\\d{3})(.{35})", groups: { 1: qualifier, 2: material } }      - clean: { columns: [po_number, quantity, unit, material], strip: true }      - default: { column: segnum, value: "000000" }                  # the control record has none      - parse-number: { column: quantity, decimal-separator: "." }    # 120.000 is 120      - fill-down: { columns: [po_number], reset-when: { column: segment, in: [EDI_DC40] } }                    # the PO, on its IDoc      - fill-down: { columns: [item, quantity, unit], reset-when: { column: segment, in: [EDI_DC40, E2EDP01, E2EDS01] } }   # the item, on its E2EDP19

Limites

  • Un second regex-extract qui écrit la même colonne y met null là où il ne correspond pas: le DOCNUM est lu par un seul motif.
  • Les lignes sont une lecture filtrée des enregistrements: un poste sans E2EDP19 002 n'a pas de ligne.
  • Fichier synthétique, format simplifié, commandes et articles fictifs.

Ventes · SAP

Le client envoie ses commandes en IDoc.

Un fichier à plat, largeur fixe.

Deux IDocs ORDERS05

Le problème

La commande est loin de l'article.

  • Le numéro dans E2EDK02.
  • L'article dans E2EDP19, plus bas.

Ce qui n'est pas modifié

Le SAP du client reste tel quel.

  • Son fichier, son format.
  • Aucun middleware.

Le piège

Un IDoc sans numéro de commande.

  • Il ne doit pas prendre celui d'avant.
  • Sinon la ligne part sur la mauvaise commande.

Ce qu'il a fallu écrire

reset-when: { in: [EDI_DC40] }

Une ligne.

  • Le numéro repart à chaque IDoc.
  • Chaque ligne garde sa commande.
  • Deux manifestes, 50 lignes.

Le résultat

Trois lignes de commande.

  • ART-10442 × 120 PCE, ART-20017 × 48,5 KGM.
  • Le second IDoc reste sans numéro.

La limite

Un poste sans article n'a pas de ligne.

  • Les lignes sont une lecture filtrée des enregistrements.
