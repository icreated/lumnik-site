Le produit dans PostgreSQL et sa catégorie dans Oracle

Objectif Relier chaque produit PostgreSQL à sa catégorie Oracle, en lecture seule, sans perdre ni doubler un produit.

Les produits vivent dans PostgreSQL, leurs catégories dans Oracle. Deux connecteurs jdbc les lisent sans rien y écrire, et une entité les joint.

  • 40 234 produits, 63 catégories
  • chaque produit porte sa catégorie quand elle existe
  • le produit sans catégorie reste, avec des champs vides

Les mots de passe des deux bases vont dans lm secret

Le manifeste nomme le secret avec password_env. La valeur passe par stdin.

  • jamais dans argv
  • jamais dans le manifeste
  1. 1
    Ordre

    Le hub cherche d'abord dans son environnement, puis dans lm secret.

  2. 2
    Sans redémarrage

    Aucune variable à ajouter au hub: le secret suffit.

PostgreSQL et Oracle, lus en lecture seule

Deux connecteurs jdbc lisent les deux bases en lecture seule.

  • PostgreSQL: 40 234 produits
  • Oracle Free 23ai: 63 catégories, par le pilote ojdbc17 embarqué
  1. 1
    Noms Oracle

    rename ramène les colonnes Oracle en minuscules; target nomme la table du hub.

  2. 2
    Conservation

    IN = OUT pour les deux sources: aucune ligne écartée.

Ce que prouve cette étape

Les deux bases sont lues en entier, chacune par son dialecte.

Le produit porte sa catégorie Oracle

MergedProductB joint chaque produit PostgreSQL à sa catégorie Oracle.

  • clé: m_product_category_id
  1. 1
    Clé métier

    L'identifiant de catégorie est du texte des deux côtés: un NUMBER Oracle ne s'écrirait pas comme un entier PostgreSQL.

  2. 2
    Jointure gauche

    Un produit sans catégorie reste dans l'entité.

Ce que prouve cette étape

Deux bases de deux éditeurs deviennent une seule fiche, déclarée dans un manifeste.

manifests/30-product-with-category.yaml
kind: Entityname: MergedProductBdescription: Products from PostgreSQL enriched with their Oracle category.match: [product_id]scopes: [catalogue]sources:  - table: t_m_product_b    map:      m_product_id: product_id      m_product_category_id: category_id      name: product_name      description: product_description      isactive: product_activejoins:  - table: t_m_product_category_b    from: category_id    to: m_product_category_id    map:      name: category_name      description: category_description      isactive: category_active

Chaque produit, une seule fois

Chaque produit apparaît une seule fois.

  • 1024944 et 1025082: catégorie Pompes

  1. 1
    Cardinalité

    40 234 lignes dans l'entité, autant que dans PostgreSQL.

  2. 2
    Partage

    Une catégorie enrichit plusieurs produits sans les fusionner.

Catalogue · deux bases

Le produit est dans PostgreSQL.

Sa catégorie est dans Oracle.

Deux bases héritées, aucune ne voit l'autre.

Catalogue synthétique

Le problème

Une fiche produit demande les deux.

  • Migrer une base coûte un projet.
  • Un ETL maison est un script de plus.
  • Une jointure ratée fait disparaître des produits.

Rien n'est migré

Les deux bases restent où elles sont.

  • Deux comptes en lecture seule.
  • Les mots de passe dans lm secret.
  • Aucune application à développer.

Ce qu'il a fallu écrire

joins:
  - table: t_m_product_category_b

Une jointure entre les deux bases.

Le scénario complet tient en 3 fichiers de déclaration, 68 lignes.

Ce que montre la fiche

4120.300.042, catégorie Pompes.

  • Le produit vient de PostgreSQL.
  • Pompes vient d'Oracle.
  • 40 234 produits, chacun une seule fois.

Rejeu du 3 novembre 2026.

Rien ne disparaît

Un produit sans catégorie reste.

  • 9999999 n'a pas de catégorie dans Oracle.
  • Il est sur la fiche, catégorie vide.
  • La jointure est une jointure gauche.

La limite

Le mode full ne voit pas une ligne modifiée sur place.

  • Il relit ce qui suit la dernière clé.
  • Pour suivre les mises à jour: une colonne de watermark.
  • Oracle est réservé à l'édition Pro.
