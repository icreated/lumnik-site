Une fiche produit, deux bases : PostgreSQL et Oracle restent où elles sont.

Les produits vivent dans PostgreSQL, leurs catégories dans Oracle. Deux connecteurs jdbc les lisent sans rien y écrire, et une entité les joint : 40 234 produits, chacun avec sa catégorie quand elle existe.

Les mots de passe des deux bases vont dans lm secret

Le manifeste nomme le secret avec password_env ; la valeur passe par stdin, jamais par argv ni par le manifeste.

  1. 1
    Ordre

    Le hub cherche d'abord dans son environnement, puis dans lm secret.

  2. 2
    Sans redémarrage

    Aucune variable à ajouter au hub : le secret suffit.

Ce que prouve cette étape

Un connecteur jdbc écrit en manifeste obtient son mot de passe sans toucher au hub.

$ lm secret set MERGE_DB_POSTGRES_PASSWORD -
Created secret "MERGE_DB_POSTGRES_PASSWORD"

$ lm secret set MERGE_DB_ORACLE_PASSWORD -
Created secret "MERGE_DB_ORACLE_PASSWORD"
secret

PostgreSQL et Oracle, lus en lecture seule

40 234 produits côté PostgreSQL, 63 catégories côté Oracle Free 23ai, par le pilote ojdbc17 embarqué.

  1. 1
    Noms Oracle

    rename ramène les colonnes Oracle en minuscules ; target nomme la table du hub.

  2. 2
    Conservation

    IN = OUT pour les deux sources : aucune ligne écartée.

Ce que prouve cette étape

Les deux bases sont lues en entier, chacune par son dialecte.

Le produit porte sa catégorie Oracle

MergedProductB joint les produits PostgreSQL à leurs catégories Oracle par m_product_category_id.

  1. 1
    Clé métier

    L'identifiant de catégorie est du texte des deux côtés : un NUMBER Oracle ne s'écrirait pas comme un entier PostgreSQL.

  2. 2
    Jointure gauche

    Un produit sans catégorie reste dans l'entité.

Ce que prouve cette étape

Deux bases de deux éditeurs deviennent une seule fiche, déclarée dans un manifeste.

manifests/30-product-with-category.yaml
kind: Entityname: MergedProductBdescription: Products from PostgreSQL enriched with their Oracle category.match: [product_id]scopes: [catalogue]sources:  - table: t_m_product_b    map:      m_product_id: product_id      m_product_category_id: category_id      name: product_name      description: product_description      isactive: product_activejoins:  - table: t_m_product_category_b    from: category_id    to: m_product_category_id    map:      name: category_name      description: category_description      isactive: category_active

Chaque produit, une seule fois

Deux produits de la catégorie Pompes la lisent tous les deux ; le produit témoin sans catégorie reste, avec des champs nuls.

  1. 1
    Cardinalité

    40 234 lignes dans l'entité, autant que dans PostgreSQL.

  2. 2
    Partage

    Une catégorie enrichit plusieurs produits sans les fusionner.

Ce que prouve cette étape

La jointure garde tous les produits et n'en duplique aucun.
