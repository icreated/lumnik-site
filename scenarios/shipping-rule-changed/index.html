La règle a changé au 1er janvier : chaque commande dit quelle version l'a calculée.

Les frais de port sont calculés par un script Kotlin que fournit l'opérateur du hub : port offert dès 150,00 en décembre, dès 200,00 à partir de janvier. L'opérateur remplace le script. Des mois plus tard, un auditeur demande pourquoi une commande de 172,50 n'a pas payé de port en décembre, et en a payé en janvier.

L'opérateur dépose la règle

Le script est un fichier du dossier de scripts du hub, que seul l'opérateur remplit. lm hook scripts montre son empreinte SHA-256 : c'est elle qui identifie la version de la règle.

Pourquoi le même montant n'a pas le même port

L'entité expose le run qui a écrit chaque commande. CMD-2402 (décembre) et CMD-2501 (janvier) ont 172,50 de marchandises : port 0,00 pour l'une, 12,90 pour l'autre. lm run get sur le run de CMD-2402 nomme la version 1 de la règle.

  1. 1
    _run_id

    Le run qui a écrit la ligne.

Ce que prouve cette étape

Commande, run, version de la règle : la chaîne se lit avec lm, sans accès au serveur.

Limites

  • Le run liste les versions qu'il a appliquées, pas quelles lignes sont passées par laquelle : un script remplacé pendant un run laisse ses lignes sous les deux versions.
  • L'empreinte identifie un texte, pas son contenu : garder les versions du script reste le travail de l'opérateur.
  • Commandes synthétiques.
