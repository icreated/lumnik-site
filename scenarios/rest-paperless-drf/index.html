Paperless-ngx: des correspondants ajoutés et supprimés pendant la lecture

Objectif Lire tous les correspondants d'une archive Paperless-ngx par son API, sans en perdre un quand la liste change pendant la lecture, et être prévenu quand elle change sans arrêt.

Un vrai Paperless-ngx 2.13 et 100 correspondants, lus dix par page.

  • au calme: les 100, le count de chaque page vérifié;
  • un correspondant supprimé pendant la lecture: les pages se décalent, la liste est relue;
  • de nouveaux correspondants sans arrêt: le run refuse de se dire complet.

100 correspondants, dix par page

L'image officielle de Paperless-ngx 2.13, avec Redis. Le script crée 100 correspondants par l'API. Chaque page de Django REST Framework donne le total (count) et l'adresse de la suivante (next).

  • count: 100
  • next: ?page=2&page_size=10
  1. 1
    Un mot de passe jetable

    Donné à Paperless et au hub comme secret lm. Il n'est jamais écrit dans les preuves.

Ce que prouve cette étape

On lit l'archive par son API, sans la toucher.

Les 100 correspondants en une ligne

pagination: { kind: drf-page }. Le hub suit next, lit results et compare le nombre de lignes lues au count.

  • 10 pages, une par seconde
  • 100 sur 100
  1. 1
    Un témoin

    Si le hub lit moins de lignes que le count annoncé, le run échoue au lieu de se dire complet.

Ce que prouve cette étape

Une ligne suffit pour lire une API Django REST.

manifests/10-correspondents.yaml
apiVersion: connectors.lumnik.io/v1kind: Connectormetadata:  name: scenario-paperless-a  connector_type: rest-generic  scopes: [archive]spec:  base_url: http://host.docker.internal:9330/api  auth:    kind: basic    username: lumnik    password_env: SCENARIO_PAPERLESS_A_PASSWORD  default_rate_limit: 1/s                              # a gentle reader: ten pages take ten seconds  endpoints:    - id: correspondents      path: /correspondents/?page_size=10      method: GET      pagination: { kind: drf-page }                   # follows $.next, reads $.results, checks $.count      target:        kind: hybrid        table: ext.scenario_paperless_a        unique_key: $.id        promote:          - { name: name, path: $.name, type: text }          - { name: documents, path: $.document_count, type: integer }

Un correspondant supprimé: la liste est relue

Pendant la lecture, on supprime Correspondant 001, déjà lu en page 1. Toutes les lignes suivantes remontent d'une place: une ligne n'est sur aucune page. Le count passe de 100 à 99, alors le hub relit la liste depuis la page 1 (#1771).

  • IN 159: 60 lignes, puis les 99
  • les 99 restants sont tous dans la table

Une liste qui ne s'arrête pas: le run échoue

Un nouveau correspondant arrive chaque seconde. Le count bouge pendant la lecture, puis encore pendant la relecture. Le run échoue et donne les deux totaux.

  • 101, puis 102
  1. 1
    Quoi faire

    Le lancer à une heure calme (window:), ou lire de plus grandes pages.

Limites

  • Un correspondant supprimé reste dans la table du hub: une lecture complète ajoute et met à jour, elle n'efface pas.
  • La relecture compte deux fois les lignes lues deux fois dans IN; l'upsert n'en garde qu'une.
  • 100 correspondants fictifs, créés par le script.

Archive · documents

Les correspondants sont dans Paperless-ngx.

Il faut tous les lire, chaque nuit.

Paperless-ngx 2.13, 100 correspondants

Le problème

L'API rend la liste par pages.

  • Dix par page, numérotées.
  • Pendant ce temps, l'équipe travaille.

Ce qui n'est pas modifié

L'archive reste telle quelle.

  • Son API, un compte en lecture.
  • Aucun module, aucun réglage.

Le piège

Une suppression décale les pages.

  • Un correspondant de la page 1 disparaît.
  • Un autre ne tombe sur aucune page.

Ce qu'il a fallu écrire

pagination: { kind: drf-page }

Une ligne.

  • Le count de chaque page est vérifié.
  • S'il bouge, la liste est relue.
  • Un connecteur de 27 lignes.

Quand ça ne s'arrête pas

Le run échoue, il ne ment pas.

  • La liste bouge encore à la relecture.
  • Le message donne les deux totaux.

Ce qui a été corrigé

Un trou trouvé, une correction.

  • Avant: Completed, un correspondant manquant.
  • Maintenant: relu, ou refusé (#1771).
