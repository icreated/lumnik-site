FastAPI: les livraisons d'un service maison sans export

Objectif Lire toutes les livraisons d'un service FastAPI maison par son API, sans demander d'export à son équipe, et savoir pourquoi une page de 500 lignes est refusée.

Un vrai service FastAPI avec fastapi-pagination 0.16.1 et 130 livraisons fictives.

  • au calme: les 130 en trois pages;
  • 500 par page: la bibliothèque refuse, rien n'est ingéré;
  • un size écrit dans le path: refusé dès lm apply (#1789).

Les 130 livraisons en une ligne

pagination: { kind: fastapi }. Le hub envoie page et size, lit items et s'arrête au nombre de pages annoncé.

  • size: 50 par défaut
  • trois requêtes, 130 sur 130

500 par page: la bibliothèque refuse

Le même connecteur avec size: 500. fastapi-pagination accepte au plus 100 et répond 422. Le run échoue avec la phrase de la bibliothèque et n'ingère rien.

  • size: la taille de page, envoyée par le hub
  1. 1
    Quoi faire

    Déclarer un size de 100 ou moins, ou demander à l'équipe de relever sa limite.

Ce que prouve cette étape

Une API qui refuse ne passe pas pour une liste vide.

Un size écrit dans le path refusé dès lm apply

path: /deliveries?size=500. Le preset envoie déjà size: la requête le porterait deux fois et l'API en garderait un. lm apply refuse et désigne spec.endpoints[0].path.

  • la taille de page se déclare dans pagination.size
  1. 1
    Avant la correction

    Le hub envoyait size=500&page=1&size=50. FastAPI gardait 50, le run disait Completed, sans rien signaler (#1789).

Limites

  • fastapi-pagination plafonne size à 100 par défaut; l'équipe du service peut changer cette limite.
  • 130 livraisons fictives, créées au démarrage du service.

Logistique · livraisons

Les livraisons sont dans un service maison.

L'équipe logistique l'a écrit en Python.

FastAPI, fastapi-pagination 0.16.1, 130 livraisons

Le problème

L'API rend la liste par pages.

  • page et size dans l'adresse.
  • Le total et le nombre de pages dans chaque réponse.

Ce qui n'est pas modifié

Le service reste tel quel.

  • Son API, telle que l'équipe l'a écrite.
  • Aucun export, aucun développement.

Ce qu'il a fallu écrire

pagination: { kind: fastapi }

Une ligne.

  • page=1, size=50, puis les suivantes.
  • Lit items, s'arrête à pages.
  • Un connecteur de 22 lignes.

Au calme

130 sur 130, en trois requêtes.

  • page=1, 2, 3, cinquante par page.
  • 130 lignes dans le hub.

Trop gros

500 par page: la bibliothèque refuse.

  • fastapi-pagination plafonne size à 100.
  • Son refus 422 arrive tel quel dans le run.
  • Rien n'est ingéré.

Ce qui a été corrigé

Un trou trouvé, une correction.

  • Avant: size=500 dans le path, envoyé deux fois, ignoré.
  • Maintenant: refusé dès lm apply (#1789).
