k8s a oublié, lumnik se souvient: qui a crashé cette nuit?

Objectif Demander quels déploiements ont crashé en boucle, après que Kubernetes a effacé leurs events, et recevoir la liste que kubectl donnait pendant l'incident.

Kubernetes garde ses events une heure. Un déploiement réparé à l'aube n'a plus d'histoire le matin:

  • un nouveau pod, Running, 0 redémarrage;
  • plus aucun event Warning.

lumnik lit les events pendant qu'ils existent et les garde; Ask répond encore quand kubectl ne sait plus.

Un cluster qui oublie vite, deux déploiements qui crashent

kind-cluster.yaml: l'API server efface les events après 3 minutes (--event-ttl=3m), au lieu d'une heure.

  • payment-api: sort en erreur après 5 secondes, redémarré en boucle
  • billing-api: la même panne
  • catalog-api: sain

lumnik-reader: un ServiceAccount qui lit les events, rien d'autre.

  1. 1
    Pourquoi 3 minutes

    Le même oubli qu'en production, accéléré pour qu'on le voie arriver.

  2. 2
    Lecture seule

    get et list sur les events: lumnik ne peut rien redémarrer.

Un connecteur, un endpoint: les events Warning

Un connecteur rest-generic sur /api/v1/events.

  • unique_key: l'uid de l'event; une relecture le met à jour, elle ne l'efface jamais
  • tls.ca_secret: la CA du cluster
  • pagination cursor: le jeton continue de Kubernetes
  • mapping: workload-key.kts écrit namespace/déploiement
  1. 1
    Pourquoi un script

    Un pod réparé change de nom; le déploiement reste. La clé survit au pod.

Ce que prouve cette étape

Le connecteur et son script sont acceptés.

manifests/10-cluster.yaml
# The cluster's own API, read-only: its Warning events about pods.# Each run keeps what it read; an event the cluster forgets afterwards stays in the hub.# The token and the CA come from the lumnik-reader ServiceAccount (lab-30-reader.yaml): lm secret set.apiVersion: connectors.lumnik.io/v1kind: Connectormetadata:  name: k8s-events  connector_type: rest-generic  scopes: [devops-event-memory]spec:  base_url: https://kubernetes.default.svc  auth: { kind: bearer, token_env: K8S_READER_TOKEN }  tls: { ca_secret: CLUSTER_CA }  defaults:    incremental: { mode: full }  endpoints:    - id: warnings      method: GET      path: /api/v1/events?fieldSelector=type%3DWarning,involvedObject.kind%3DPod      pagination: { kind: cursor, cursor_param: continue, cursor_path: $.metadata.continue, response_path: $.items }      target:        kind: hybrid        table: connector.k8s_warnings        unique_key: $.metadata.uid        promote:          - { name: event_uid,  path: "$.metadata.uid",            type: text }          - { name: namespace,  path: "$.involvedObject.namespace", type: text }          - { name: pod,        path: "$.involvedObject.name",      type: text }          - { name: reason,     path: "$.reason",                   type: text }          - { name: count,      path: "$.count",                    type: integer }          - { name: first_seen, path: "$.firstTimestamp",           type: timestamptz }          - { name: last_seen,  path: "$.lastTimestamp",            type: timestamptz }          - { name: message,    path: "$.message",                  type: text }          - { name: workload_key, type: text }       # filled by workload-key.kts      mapping:        cell:          - kotlin: { script: hooks:workload-key.kts }
manifests/workload-key.kts
// The deployment an event is about: namespace/deployment. A Deployment's pod is named// <deployment>-<replicaset hash>-<pod suffix>, and a new pod keeps the deployment, not the name.@Suppress("UNCHECKED_CAST")val cells = bindings["cells"] as MutableMap<String, Any?>val deployment = (cells["pod"] as String?)?.split("-")?.dropLast(2)?.joinToString("-")cells["workload_key"] = if (deployment.isNullOrEmpty()) null else "${cells["namespace"]}/$deployment"

Un event par ligne, gardé après l'oubli

KubernetesWarning: un event par ligne.

  • match: event_uid, pour que deux events d'un même déploiement restent deux lignes
  • label: une phrase par colonne; elle dit ce qu'est un BackOff
  1. 1
    Pourquoi des labels-phrases

    Ask lit les labels pour comprendre la question.

Ce que prouve cette étape

Limites

  • Le modèle traduit la question; «redémarré en boucle» le fait s'abstenir. Une colonne écrite par le script rendrait la formulation métier possible.
  • La clé suppose un pod de Deployment (<déploiement>-<hash>-<suffixe>): un StatefulSet ou un pod nu n'a pas de clé.
  • La mémoire commence au premier run: un event expiré avant d'être lu n'est pas retrouvé.
  • Cluster kind de démonstration: l'oubli est réel, accéléré à 3 minutes.

DevOps · post-mortem

9h. Tout est vert. Qui a crashé cette nuit?

L'astreinte prépare le post-mortem.

kubectl ne montre que le présent.

Cluster kind de démonstration

Le problème

Kubernetes efface ses events au bout d'une heure.

  • Un pod réparé est un nouveau pod: 0 redémarrage.
  • Ses events Warning expirent.
  • La question du post-mortem n'a plus de réponse dans le cluster.

Le lab

Deux déploiements crashent en boucle.

  • payment-api est réparé.
  • billing-api crashe encore.
  • Le cluster oublie ses events en 3 minutes au lieu d'une heure.

Ce qu'il a fallu écrire

unique_key: $.metadata.uid

cells["workload_key"] =
  "$namespace/$deployment"

Une clé par event, une par déploiement.

Le hub garde chaque event lu. Le scénario: 3 fichiers, 69 lignes.

Après l'oubli

kubectl: No resources found.

  • payment-api: Running, 0 redémarrage.
  • Le deuxième run ne lit plus qu'un event sur deux.

La réponse

«Quels déploiements ont eu un événement BackOff?»

  • payments/payment-api, oublié par le cluster.
  • billing/billing-api, encore en panne.

La preuve

Le témoin kubectl est pris pendant l'incident.

  • Même liste, ou le scénario échoue.
  • 6 fois sur 6, les mêmes deux déploiements.
