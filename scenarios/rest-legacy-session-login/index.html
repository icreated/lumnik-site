Une vieille app derrière un login: lumnik se connecte comme un utilisateur.

Objectif Lire les vétérinaires de Spring PetClinic, protégé par le login du serveur Tomcat, sans toucher à l'app.

Spring PetClinic d'avant Spring Boot, derrière le login du serveur (j_security_check). Pas de jeton d'API: un formulaire et un cookie de session.

  • sans auth, Tomcat rend sa page de login en 200: le hub la refuse, ce n'est pas du JSON;
  • auth: { kind: session }: le hub se connecte et garde la session, 6 vétérinaires;
  • l'app redémarre, la session est perdue: le hub se reconnecte seul, une fois.

PetClinic derrière le login de Tomcat

Le PetClinic du scénario précédent, sur Tomcat 11. L'exploitant le protège dans web.xml: login FORM du serveur, comptes dans Tomcat. Le code de l'app n'est pas touché.

  • sans session, /vets.json rend la page de login, en 200
  1. 1
    Pas de redirection

    Tomcat ne renvoie ni 401 ni 302: il rend sa page de login à la place des données.

Ce que prouve cette étape

Une session absente ressemble à une réponse normale.

La page de login n'est pas une donnée

Un connecteur sans auth. Le run échoue et nomme le Content-Type: text/html.

  1. 1
    Pas de faux zéro

    Le hub lit du JSON; une page HTML n'est jamais lue comme 0 ligne (#1644).

auth: { kind: session }

Le hub lit une page protégée, poste j_username et j_password, et garde le cookie de session (#1751). Le mot de passe est un secret lm.

  • pre-flight: GET, POST 303, GET des données
  • le run: un seul GET

    La session ouverte par le pre-flight sert au run.

Ce que prouve cette étape

Le hub se reconnecte seul, une fois

L'app redémarre: ses sessions sont perdues. Tomcat rend sa page de login avec un nouveau cookie; le hub le voit, se reconnecte, et rejoue la requête.

  1. 1
    Un seul nouveau login

    Si la session est encore refusée après, le run échoue en le disant.

Limites

  • Un formulaire simple: pas de login en JavaScript, pas de second facteur, pas de SAML ni de CAS.
  • Le cookie ne part que vers l'origine du login: un endpoint sur un autre hôte est refusé.
  • Les données de démo de PetClinic: 6 vétérinaires; un mot de passe jetable, tiré à chaque rejeu.

Clinique · vétérinaires

La vieille app de la clinique demande un login.

Il faut lire ses vétérinaires, chaque nuit.

Spring PetClinic derrière le login de Tomcat

Le problème

Pas de jeton d'API.

  • Un formulaire, un mot de passe.
  • Puis un cookie de session.

Ce qui n'est pas modifié

L'app reste telle quelle.

  • Le login est celui du serveur.
  • Le compte est un compte de la clinique.

Sans auth

Le serveur rend sa page de login.

  • En 200, en HTML.
  • Le hub la refuse: ce ne sont pas des données.

Ce qu'il a fallu écrire

auth: { kind: session }

Le hub se connecte comme un utilisateur.

  • 6 vétérinaires.
  • Un connecteur de 30 lignes.

Le redémarrage

L'app redémarre, la session est perdue.

  • Le hub se reconnecte seul, une fois.
  • Le run lit les 6 vétérinaires.

La limite

Un formulaire simple.

  • Pas de login en JavaScript.
  • Pas de second facteur.
