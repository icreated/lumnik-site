NestJS: un ticket supprimé pendant la lecture décale les pages

Objectif Lire tous les tickets d'un service NestJS par son API, ou les seuls ouverts, sans en perdre un quand le support en supprime pendant la lecture.

Un service NestJS sur nestjs-paginate et 130 tickets, dont 97 ouverts.

  • tout: les 130, en suivant le lien next;
  • les ouverts seuls: le filtre suit chaque lien, 97 lus;
  • un ticket supprimé pendant la lecture: le total bouge, la liste est relue.

130 tickets derrière nestjs-paginate

Un service NestJS 11 tel qu'une équipe l'écrit: TypeORM et nestjs-paginate 12.5. Chaque page donne le total (meta.totalItems) et l'adresse de la suivante (links.next).

  • totalItems: 130
  • next: ?page=2&limit=2&sortBy=id:ASC
  1. 1
    Un labo construit

    Docker Compose construit le service depuis lab/, versions épinglées.

Les 130 tickets en une ligne

pagination: { kind: nestjs }. Le hub suit links.next, lit data et compare les lignes lues à meta.totalItems.

  • path: limit=50, trois pages
  • 130 sur 130
  1. 1
    Un témoin

    Si le hub lit moins de lignes que le total annoncé, le run échoue au lieu de se dire complet.

Ce que prouve cette étape

Une ligne suffit pour lire une API NestJS.

manifests/10-tickets.yaml
apiVersion: connectors.lumnik.io/v1kind: Connectormetadata:  name: scenario-nestjs-a  connector_type: rest-generic  scopes: [support]spec:  base_url: http://host.docker.internal:9350  endpoints:    - id: tickets      path: "/tickets?limit=50"      method: GET      pagination: { kind: nestjs }                    # follows $.links.next, reads $.data      target:        kind: hybrid        table: ext.scenario_nestjs_a        unique_key: $.id        promote:          - { name: subject, path: $.subject, type: text }          - { name: status, path: $.status, type: text }

Le filtre suit chaque lien next

Le même connecteur, avec filter.status=$eq:open dans le path. nestjs-paginate remet le filtre dans chaque lien next: le hub n'a rien à ajouter.

  • 97 tickets, tous ouverts
  1. 1
    Pourquoi filtrer à la source

    Le service ne rend que ce qu'on lit: aucun ticket fermé n'arrive dans le hub.

Ce que prouve cette étape

Un ticket supprimé: la liste est relue

Dix par page, une par seconde. Pendant la lecture, on supprime Ticket 001, déjà lu en page 1. Les tickets suivants remontent d'une place: un ticket n'est sur aucune page. meta.totalItems passe de 130 à 129, alors le hub relit la liste (#1794).

  • default_rate_limit: 1/s, une page par seconde
  • IN 189: la première lecture, puis la relecture
  • les 129 restants sont tous dans la table
  1. 1
    Avant la correction

    Le preset ne lisait pas meta.totalItems: le run disait Completed avec un ticket en moins.

Ce que prouve cette étape

Limites

  • Un ticket supprimé reste dans la table du hub: une lecture complète ajoute et met à jour, elle n'efface pas.
  • La relecture compte deux fois les lignes lues deux fois dans IN; l'upsert n'en garde qu'une.
  • 130 tickets fictifs, en mémoire dans le service.

Support · tickets

Les tickets sont dans le service support.

Il faut tous les lire, par l'API.

NestJS 11, nestjs-paginate, 130 tickets

Le problème

L'API rend la liste par pages.

  • Chaque page donne le lien de la suivante.
  • Pendant ce temps, le support travaille.

Ce qui n'est pas modifié

Le service reste tel quel.

  • Son API, telle que l'équipe l'a écrite.
  • Aucun module, aucun réglage.

Le piège

Une suppression décale les pages.

  • Un ticket de la page 1 disparaît.
  • Un autre ne tombe sur aucune page.

Ce qu'il a fallu écrire

pagination: { kind: nestjs }

Une ligne.

  • Le lien next est suivi.
  • Le total de chaque page est vérifié.
  • Un connecteur de 21 lignes.

Un filtre

Les tickets ouverts seulement.

  • Le filtre est écrit dans le path.
  • Chaque lien next le garde: 97 lus.

Ce qui a été corrigé

Un trou trouvé, une correction.

  • Avant: Completed, un ticket manquant.
  • Maintenant: la liste est relue (#1794).
