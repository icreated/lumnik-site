OPEN, puis CLOSED, en moins d'une minute

Un kind:Workflow déclare le cycle d'une porte sur la vue enrichie : OPEN au départ, CLOSED terminal, une dormance au-delà d'une minute, et la phrase de sa décision.

  1. 1
    Clé et ordre

    door_incident_id suit chaque ouverture ; occurred_at, l'heure du capteur, désigne son événement courant.

  2. 2
    Contexte

    Le message cite le laboratoire et la personne responsable ; fields ajoute le contenu et la criticité.

Ce que prouve cette étape

Le cycle est déclaré, pas codé.

manifests/40-door-workflow.yaml
apiVersion: apps.lumnik.io/v1kind: Workflowmetadata:  name: scenario-freezer-door-fspec:  scope: cold-chain  provenance: declared  on:    table: connector.v_scenariofreezerdooreventf    column: door_state    key: door_incident_id    order: occurred_at  dormancy:    after: 1m    message: "{freezer_id} ({laboratory}): door {state} since {since}. Owner: {owner}"    fields: [contents, criticality]  states:    - code: OPEN      label: "Open"      initial: true    - code: CLOSED      label: "Closed"      terminal: true  transitions:    - { from: [OPEN], to: CLOSED }

Limites

  • Le workflow connaît le dernier événement reçu : un OPEN qui dure peut aussi être un CLOSED perdu avant le broker. Il détecte un silence, pas l'état physique de la porte.
  • La dormance se compte à partir de la première observation par lumnik, pas de l'occurred_at du capteur.
  • Pour la démonstration, le balayage tourne toutes les 5 secondes ; il tourne toutes les 15 minutes par défaut. Le seuil métier reste le minimum accepté, 1 minute.
  • Données synthétiques.
