Le cluster brûle, k9s dit Running: quel pod regarder d'abord?

Objectif Demander à son cluster Kubernetes quels pods traiter en premier, et recevoir la liste triée par la règle de l'astreinte, vérifiée contre kubectl.

Un vrai cluster, cinq équipes, cinq pods cassés par Kubernetes lui-même:

  • l'API des pods: état, redémarrages, raison de la dernière mort;
  • metrics.k8s.io: ce que chaque pod consomme maintenant;
  • les events Warning.

Une règle Kotlin de l'astreinte fixe la priorité; le modèle traduit la question, il ne décide rien.

Cinq pods cassés par Kubernetes lui-même

Cinq namespaces, un par équipe. Chaque panne est réelle:

  • payment-api: remplit sa mémoire au-delà de 64Mi, le noyau le tue (OOMKilled)
  • billing-api: sonde liveness en échec, redémarrée sans fin
  • checkout-worker: sonde readiness sur un chemin absent, jamais Ready
  • storefront: monte une ConfigMap qui n'existe pas
  • catalog-api: boucle CPU sous une limite de 100m

lumnik-reader: un ServiceAccount qui lit pods, events et metrics, rien d'autre.

  1. 1
    Pourquoi un vrai cluster

    Un public DevOps repère une donnée fabriquée; ici chaque état vient du kubelet.

  2. 2
    Lecture seule

    get et list sur trois ressources: lumnik ne peut rien redémarrer.

Ce que prouve cette étape

kubectl montre quatre pods en panne et un pod qui a l'air sain.

Un connecteur, trois endpoints

Un connecteur rest-generic, une API: celle du cluster.

  • tls.ca_secret: la CA du cluster, lue depuis le ServiceAccount
  • pagination cursor: le jeton continue de Kubernetes
  • transform: parse_quantity: 100m devient 0.1 cœur, 64Mi 67108864 octets
  • promote sans path: une colonne que le script remplit
  • mapping: le script Kotlin de l'astreinte, sur chaque pod lu
  1. 1
    Pourquoi un script

    La priorité est une règle d'astreinte: écrite une fois, appliquée à chaque pod, jamais devinée par le modèle.

  2. 2
    La vraie cause

    kubectl affiche CrashLoopBackOff; le script lit lastState et dit OOMKilled.

Ce que prouve cette étape

Les pods, leur consommation et leurs events arrivent avec une priorité calculée.

manifests/pod-triage.kts
// The operator's triage rule, over one pod's own state (the pods API). Deterministic: the model never decides it.//   critical — the kernel killed it for memory, or it loops on restarts (CrashLoopBackOff)//   high     — it is not ready: a probe fails, or it cannot start (ContainerCreating, ImagePullBackOff…)//   medium   — it is ready but has restarted//   none     — nothing in its state// Saturation is not here: usage comes from metrics.k8s.io, another endpoint.@Suppress("UNCHECKED_CAST")val cells = bindings["cells"] as MutableMap<String, Any?>val waiting = cells["waiting_reason"] as String?val terminated = cells["last_terminated_reason"] as String?val restarts = (cells["restarts"] as Number?)?.toInt() ?: 0val ready = cells["ready"] == truecells["pod_key"] = "${cells["namespace"]}/${cells["pod"]}"val (priority, signal) = when {    terminated == "OOMKilled" -> "critical" to "OOMKilled, $restarts restarts"    waiting == "CrashLoopBackOff" -> "critical" to "CrashLoopBackOff, $restarts restarts"    !ready -> "high" to (waiting ?: "not ready")    restarts > 0 -> "medium" to "$restarts restarts"    else -> "none" to ""}cells["priority"] = prioritycells["priority_rank"] = mapOf("critical" to 1, "high" to 2, "medium" to 3, "none" to 4).getValue(priority)cells["signal"] = signal
manifests/pod-key.kts
// The key of the pod a row is about: namespace/pod — the pods, their usage and their events join on it.@Suppress("UNCHECKED_CAST")val cells = bindings["cells"] as MutableMap<String, Any?>cells["pod_key"] = "${cells["namespace"]}/${cells["pod"]}"

Un pod, son état et ce qu'il consomme

KubernetesPod rattache la consommation à son pod.

  • match: pod_key, la clé namespace/pod que le script écrit
  • joins: metrics.k8s.io, par pod_key
  • label: une phrase par colonne; elle dit la règle (none = rien à investiguer, saturé à 90% de la limite)

KubernetesWarning: un event par ligne.

  1. 1
    Pourquoi des labels-phrases

    Ask lit les labels pour comprendre la question: un seuil écrit est un seuil compris.

Ce que prouve cette étape

État et consommation se lisent sur une ligne par pod.

«Quels pods dois-je analyser en priorité?»

Ask traduit la question en SQL, en lecture seule, sur la vue de l'entité.

  • WHERE priority IN ('critical','high','medium') OR cpu >= 0.9 * cpu_limit
  • ORDER BY priority_rank

Cinq pods; catalog-api y entre par sa consommation.

  1. 1
    Vérifié contre kubectl

    Le runner recalcule la règle depuis kubectl et compare: même liste, ou le scénario échoue.

  2. 2
    Stable

    8 fois sur 8, le même SQL et les mêmes cinq pods.

Limites

  • Le modèle traduit la question; une autre formulation peut produire un autre SQL. Le SQL est affiché pour être relu.
  • La saturation combine deux API: c'est le SQL qui la calcule, pas le script. Une colonne calculée par le hub la rendrait déterministe.
  • Un premier conteneur par pod seulement: un pod à plusieurs conteneurs est jugé sur le premier.
  • Cluster kind de démonstration: les pannes sont réelles, le cluster est petit.

Le problème

Trois API, aucune vue d'ensemble.

  • Les pods disent leur état.
  • metrics.k8s.io dit leur consommation.
  • Les events disent ce qui alerte.

Le piège

catalog-api: Running, 1/1, aucun event.

  • Il tourne à 100% de sa limite CPU.
  • Seule metrics.k8s.io le montre.

Ce qu'il a fallu écrire

cells["priority"] = when {

  !ready -> "high"

Cinq pods, du critique au saturé.
