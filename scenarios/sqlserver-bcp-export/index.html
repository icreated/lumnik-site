SQL Server lu par son propre export: bcp

Objectif Lire les commandes d'une base SQL Server alors que lumnik n'a pas de dialecte pour elle: par l'export bcp, une ligne décalée mise de côté avec sa raison.

Le monde .NET garde ses données dans SQL Server. jdbc-generic parle PostgreSQL et Oracle: demandé pour jdbc:sqlserver, il refuse avant toute connexion et dit ce qu'il a. Le chemin qui marche est l'outil d'export de SQL Server, bcp.

  • le refus, nommé, au validate
  • bcp: pas d'en-tête, pas de guillemets
  • un ; dans un nom décale la ligne: elle est mise de côté

jdbc-generic refuse SQL Server par son nom

L'intégrateur essaie d'abord la lecture directe. Le manifeste est refusé au validate, sans connexion.

  • url: jdbc:sqlserver, aucun dialecte installé ne l'accepte
  • le message dit ceux du hub: oracle, postgres
  1. 1
    Avant toute connexion

    Rien n'est tenté contre la base.

  2. 2
    Le geste

    Installer un provider, ou passer par un export.

Ce que prouve cette étape

Un refus qui nomme la correction.

L'export bcp lu, la ligne décalée écartée

Le DBA planifie bcp queryout avec un login en lecture seule, vers un serveur SFTP.

  • has_header: false, bcp n'écrit pas d'en-tête
  • columns: les six colonnes déclarées
  • parse-date: le format que bcp écrit, 2026-10-02 08:15:00.0000000
  • SO-0004, Dupont; Fils: sept valeurs pour six colonnes, mise de côté telle que lue
  1. 1
    6 lignes lues

    5 écrites, 1 mise de côté.

  2. 2
    Raison

    Le fichier, le numéro de ligne et les valeurs lues.

Ce que prouve cette étape

Une ligne décalée n'arrive jamais avec ses champs mélangés.

manifests/20-bcp-orders.yaml

Limites

  • Pas de dialecte SQL Server: un provider lirait la table directement, et en incrémental. Il n'existe pas.
  • Choisir un séparateur que les données ne contiennent pas: une tabulation ou un fichier de format bcp. Le scénario garde ; pour montrer le défaut.
  • Un export est une photo: chaque run lit ce que le dernier bcp a écrit.
  • Six commandes synthétiques.
