Une commande modifiée pendant la lecture n'est pas perdue

Objectif Ne lire chaque nuit que les commandes modifiées, sans perdre celles qui changent pendant la lecture.

Une API de commandes sait répondre à « ce qui a changé depuis telle date ». lumnik la lit en entier une fois, puis chaque nuit seulement ce qui a bougé.

  • la marque reculée d'une marge;
  • une commande modifiée pendant un run arrive au run suivant;
  • chaque date rangée comme une date.

Limites

  • La marge relit les commandes modifiées dans cet intervalle ; elles sont mises à jour, pas dupliquées.
  • Fonctionne quand updated_at porte un fuseau horaire ; un numéro de version ou une date seule est envoyé tel quel.
  • API simulée, commandes synthétiques.

Ventes · API de commandes

L'API dit ce qui a changé.

Chaque nuit, seulement ça.

300 commandes, API simulée

Le problème

Une commande change pendant la lecture.

  • Déjà lue, elle bouge encore.
  • La marque suivante passe après.

Ce qui n'est pas modifié

L'API reste telle quelle.

  • Son paramètre updated_since.
  • Aucun déclencheur à ajouter.

Le piège

Un changement entre deux nuits.

  • Trop tard pour ce run.
  • Trop tôt pour le suivant.

Ce qu'il a fallu écrire

incremental: { mode: watermark }

Une ligne.

  • La marque reculée d'une marge.
  • Ce qui est relu est mis à jour.
  • Un manifeste, 31 lignes.

Le résultat

SO-00101 arrive invoiced.

  • Au run suivant.
  • Sans doublon.

La limite

Il faut une date avec fuseau.

  • Un numéro de version est envoyé tel quel.
