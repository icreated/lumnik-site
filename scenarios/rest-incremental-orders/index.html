L'API qui n'envoie que ce qui a changé : une commande modifiée pendant la lecture n'est pas perdue.

Une API de commandes sait répondre à « ce qui a changé depuis telle date ». lumnik la lit en entier une fois, puis chaque nuit seulement ce qui a bougé. Une commande modifiée pendant qu'un run lit encore les pages suivantes aurait pu passer entre deux nuits : le run suivant repart un peu avant sa dernière marque, et la récupère.

Une première lecture complète, chaque date rangée comme une date

Sans marque, le run lit les 300 commandes. L'API envoie updated_at sous forme de texte ; lumnik le range comme une date, sans transformation à déclarer.

Une commande déjà lue change pendant le run

120 commandes ont changé. Pendant que le run lit, SO-00101, déjà lue au statut shipped, passe à invoiced ; puis SO-00219, sur une page encore à lire, change aussi. Le run se termine : sa marque est maintenant la date de SO-00219, plus récente que le second changement de SO-00101.

SO-00101 arrive invoiced

Le run suivant repart un peu avant la marque, de la durée du run précédent plus une minute. SO-00101 revient avec son statut invoiced. Les commandes relues une seconde fois sont simplement mises à jour.

Limites

  • La marge relit les commandes modifiées dans cet intervalle ; elles sont mises à jour, pas dupliquées.
  • Fonctionne quand updated_at porte un fuseau horaire ; un numéro de version ou une date seule est envoyé tel quel.
  • API simulée, commandes synthétiques.
