Les lignes de commande d'un fichier EDI à plat lues à leur place

Objectif Lire en colonnes les lignes de commande d'un fichier EDI à largeur fixe, sans outil de mapping.

Un fabricant et son logisticien s'échangent des fichiers à plat. Aucun séparateur: chaque champ a sa place et sa largeur.

  • l'en-tête écarté et compté;
  • onze champs découpés à leur place;
  • les accents justes, même dans un fichier d'une ligne.

Le fichier lu ligne à ligne, l'en-tête écarté

lines: true lit une ligne par enregistrement. filter-where écarte l'en-tête. regex-extract découpe onze champs à leur place.

  • 7 lignes lues
  • 6 écrites, l'en-tête compté
  1. 1
    Largeurs

    17, 10, 10, 40, 50…: une seule expression.

  2. 2
    Fin de fichier

    La dernière ligne, sans retour, est lue.

Ce que prouve cette étape

7 = 6 + 1: six lignes de commande écrites, l'en-tête écarté et compté.

manifests/10-order-lines.yaml
apiVersion: connectors.lumnik.io/v1kind: Connectormetadata:  name: scenario-edi-cc-b  connector_type: csv-file  scopes: [logistics-b]spec:  transport:    kind: local    path: /tmp/lumnik-scenario/edi-flat-order-lines/b/ZINT_CC_*.txt   # one file per order the ERP sends  parser:    lines: true                        # one line = one row, no separator to guess  after_process: none  mapping:    dataset:      - filter-where: { column: line, regex: ".{27}EC.*" }   # order lines carry a customer code; the header does not    cell:      - regex-extract:                 # every field at its place and width          column: line          required: true          pattern: "^(.{17})(.{10})(.{10})(.{40})(.{50})(.{8})(.{3})(.{12})(.{12})(.{40})(.{10})(.{4})(.*)$"          groups: { 3: customer, 4: customer_name, 5: address, 6: postcode, 7: country, 8: order_no,                    9: article, 10: label, 11: quantity, 12: unit, 13: line_id }      - clean: { columns: [customer, customer_name, address, postcode, country, order_no, article, label,                           quantity, unit, line_id], strip: true }      - parse-number: { column: quantity, decimal-separator: "." }

Limites

  • Les largeurs sont celles du fichier: si l'ERP change sa mise en page, l'expression change avec lui.
  • Un libellé coupé par l'ERP reste coupé: lumnik ne retrouve pas ce qui n'a pas été envoyé.
  • Fichiers synthétiques, sur le gabarit d'un échange réel.

Logistique · EDI à plat

Les commandes arrivent en fichier à plat.

Une ligne par article, chaque champ à sa place.

ISO-8859-1, largeur fixe

Le problème

Aucun séparateur.

  • Un champ, c'est une position et une largeur.
  • Un outil de mapping coûte cher.

Ce qui n'est pas modifié

L'ERP écrit comme avant.

  • Le même fichier, le même dossier.
  • Aucun format à négocier.

Le piège

Des accents dans un petit fichier.

  • Une seule ligne, un seul é.
  • Trop peu pour deviner l'encodage.

Ce qu'il a fallu écrire

lines: true

Une ligne.

  • Une ligne du fichier, une ligne de table.
  • Les champs découpés à leur place.
  • Deux manifestes, 47 lignes.

Le résultat

Six lignes de commande en colonnes.

  • Client, commande, article, quantité.
  • « Couverture à barres », accent compris.

La limite

Les largeurs sont celles du fichier.

  • Si l'ERP change sa mise en page, le manifeste change avec lui.
