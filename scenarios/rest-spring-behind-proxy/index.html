L'appli Spring derrière un proxy: on nomme le framework, la clé reste le SKU.

Objectif Lire tout le stock d'une application Spring Data REST maison, page par page, et garder chaque produit sous son SKU, quel que soit l'hôte par lequel on l'atteint.

Un ancien prestataire a laissé une application de stock en Spring Data REST, derrière nginx. lumnik la lit avec le preset spring-hateoas:

  • ses liens pointent vers son nom interne: le run refuse de les suivre et le dit;
  • une propriété côté application, et les 63 pages passent;
  • chaque produit est rangé sous son SKU, lu dans son lien: la nuit suivante, aucune copie.

Spring Data REST derrière nginx

Une vraie application Spring Boot 3.4: un dépôt de produits exposé par Spring Data REST, 1 250 produits, nginx devant.

  • _embedded.products: les produits de la page
  • _links.next.href: la page suivante
  • _links.self.href: le seul endroit où figure le SKU
  1. 1
    Pourquoi le lien

    Spring Data REST ne met pas l'identifiant dans le corps: il le met dans le lien du produit.

  2. 2
    Le piège

    Sans réglage, Spring fabrique ses liens avec l'hôte que nginx appelle: inventory:8080.

Ce que prouve cette étape

Les liens renvoyés nomment l'hôte interne.

manifests/lab-docker-compose.yml
# The stock application of an earlier provider: Spring Data REST behind nginx.name: lumnik-spring-inventoryservices:  inventory:    build: ../run/inventory-app    environment:      # none: Spring builds its links from the host nginx called, inventory:8080.      # framework: it reads X-Forwarded-Host, the host the caller used — the one-line fix.      SERVER_FORWARD_HEADERS_STRATEGY: ${FORWARD_HEADERS:-none}  proxy:    image: nginx:1.27-alpine    ports: ["${INVENTORY_PORT:-9230}:80"]    volumes: ["./lab-nginx.conf:/etc/nginx/conf.d/default.conf:ro"]    depends_on: [inventory]
manifests/lab-nginx.conf
# The in-house reverse proxy: it forwards the caller's host, as most do.server {  listen 80;  location / {    proxy_pass http://inventory:8080;    proxy_set_header X-Forwarded-Host $http_host;    proxy_set_header X-Forwarded-Proto $scheme;  }}

On nomme le framework

Un connecteur rest-generic.

  • pagination: spring-hateoas: suit _links.next.href, lit _embedded.products
  • total_path: le total publié par l'application, témoin du compte
  • unique_key: le dernier segment du lien du produit, son SKU
  • promote: le même SKU en colonne
  1. 1
    Clé stable

    La clé ne garde pas l'hôte: un passage en https ou un autre nom ne la change pas.

Ce que prouve cette étape

Le connecteur est accepté.

manifests/10-inventory.yaml
apiVersion: connectors.lumnik.io/v1kind: Connectormetadata:  name: scenario-inventory-a  connector_type: rest-generic  scopes: [inventory]spec:  base_url: http://host.docker.internal:9230  endpoints:    - id: products      path: /products      method: GET      pagination: { kind: spring-hateoas, items: products, total_path: $.page.totalElements }      target:        kind: hybrid        table: ext.scenario_inventory_a        unique_key: { path: $._links.self.href, transform: last_path_segment }        promote:          - { name: sku, path: $._links.self.href, transform: last_path_segment, type: text }          - { name: name, path: $.name, type: text }          - { name: warehouse, path: $.warehouse, type: text }          - { name: stock, path: $.stock, type: integer }

Page 2 vers l'hôte interne: le run refuse

Le lien suivant pointe vers http://inventory:8080. lumnik ne suit un lien que vers l'hôte du connecteur: le run échoue et nomme l'hôte.

  1. 1
    Pourquoi refuser

    Un lien venu de la réponse ne peut pas envoyer le hub vers un autre serveur.

  2. 2
    IN 0

    Aucune liste partielle n'est annoncée verte.

Limites

  • La clé est le dernier segment du lien: le lien doit finir par l'identifiant, comme Spring Data REST le fait par défaut.
  • Un produit dont le lien n'a pas de segment fait échouer le run, en nommant la clé.
  • Le refus de l'hôte interne demande une correction côté application ou proxy: lumnik ne réécrit pas les liens.
  • Application Spring de démonstration, données synthétiques.

Intégration · application maison

Une appli de stock en Spring, laissée par un ancien prestataire.

Il faut lire tout le stock, chaque nuit.

Application et données de démonstration

Le problème

L'API ne donne pas l'identifiant.

  • Le SKU n'est que dans le lien de chaque produit.
  • Les liens pointent vers le nom interne du serveur.

Ce qui n'est pas modifié

Le code de l'application reste tel quel.

  • Une propriété de déploiement: faire confiance au proxy.
  • Aucun champ ajouté à l'API.

Ce qu'il a fallu écrire

pagination: { kind: spring-hateoas, items: products }
unique_key: { path: $._links.self.href,
              transform: last_path_segment }

On nomme le framework, on dit où est la clé.

Un connecteur de 24 lignes.

Le rouge

Page 2 vers inventory:8080: le run refuse.

  • Il nomme l'hôte interne.
  • Aucune liste partielle annoncée verte.

Le vert

1 250 produits, 63 pages, rangés sous leur SKU.

  • La nuit suivante: 1 250 lignes, 1 250 clés.
  • Un passage en https ne changerait aucune clé.

La limite

Le lien doit finir par l'identifiant.

  • C'est le cas par défaut avec Spring Data REST.
  • Un lien sans segment fait échouer le run, en nommant la clé.
