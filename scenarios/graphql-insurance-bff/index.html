Les listes d'un formulaire de sinistre, sans exposer le GraphQL du CRM.

Le type et le sous-type de sinistre vivent dans un CRM qui parle GraphQL. lumnik l'ingère page par page, en fait une entité canonique, et un petit BFF sert au formulaire du JSON REST stable : le schéma du CRM ne devient jamais un contrat du navigateur.

Un connecteur REST qui parle GraphQL

GraphQL n'est pas un type de connecteur : c'est une forme de requête de rest-generic. La requête et la pagination Relay sont déclarées dans le manifeste.

  1. 1
    Relay

    after, endCursor, hasNextPage : le curseur suit la réponse, trois options par page.

  2. 2
    Sonde

    lm source rest test interroge la première page avant toute ingestion.

Ce que prouve cette étape

Un CRM GraphQL se branche comme n'importe quelle source REST.

Toutes les pages, une entité canonique

Le run parcourt les pages Relay et écrit neuf options. L'entité les expose sous des noms stables : type, sous-type, ordre, disponibilité.

  1. 1
    Code inactif

    OLD_STORM_CODE est ingéré tel quel : le miroir de la source reste honnête.

  2. 2
    Contrat

    Le BFF lit l'entité, jamais le schéma du CRM.

Automobile, puis Habitation

Le formulaire demande les types, puis les sous-types du type choisi. Passer d'Automobile à Habitation remplace la liste : Collision n'y reste jamais.

  1. 1
    Actifs seulement

    Le code tempête inactif n'atteint pas le formulaire.

  2. 2
    REST stable

    Le navigateur reçoit value et label, rien du GraphQL.

Ce que prouve cette étape

Une liste dépendante ne montre que les enfants du type choisi.

Un type inconnu ne renvoie pas une autre liste

Demander les sous-types de UNKNOWN répond 404, jamais les valeurs d'un autre type.

  1. 1
    Refus

    claim type not found, en 404.

  2. 2
    Pas de repli

    Aucune liste par défaut ne remplace une réponse.

Ce que prouve cette étape

Le BFF refuse plutôt que de deviner.

Limites

  • Le CRM est synthétique, mais parle les vraies formes de requête et de réponse Relay du connecteur GraphQL de lumnik.
  • Le BFF est de taille démonstration : il appelle lm à chaque requête. Un BFF de production appellerait l'API du hub avec sa propre identité et mettrait ces listes en cache.
  • Le BFF ne fait que lire ; créer le dossier de sinistre dans le CRM sort du scénario.
  • La règle est active == true ; dates d'effet, libellés par langue et éligibilité par produit seraient d'autres règles métier.
  • Données synthétiques.
