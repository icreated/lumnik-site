Un hotfix non approuvé en production: le pipeline sort en 1.

Objectif Bloquer une mise en production quand un pod exécute une version que le comité n'a pas approuvée, par un code de sortie qu'une CI comprend.

Le catalogue des versions approuvées est un CSV. Ce qui tourne vraiment est dans le cluster. lumnik lit l'image de chaque pod par l'API Kubernetes et la joint au catalogue:

  • la version approuvée passe;
  • un hotfix poussé avec kubectl set image fait sortir la porte en 1;
  • après le rollback, la même commande repasse.

Trois services, chaque image porte sa version

Un vrai cluster kind. Chaque image est étiquetée par sa version: lumnik.local/billing-api:2.3.7.

  • billing-api et catalog-api en production
  • customer-portal en staging, une release candidate
  • release-gate-reader: un compte qui ne peut que lister les pods
  1. 1
    Pourquoi l'image

    Le tag de l'image est la version qui tourne, pas celle qu'on croit avoir livrée.

Le catalogue CSV et les pods du cluster

Deux connecteurs.

  • csv-file: le catalogue des versions approuvées, avec l'astreinte de chaque service
  • rest-generic sur /api/v1/pods: le service, l'environnement, l'image, l'heure de démarrage
  • image-version.kts: le tag de l'image devient deployed_version
  1. 1
    Clé

    unique_key: l'uid du pod. Un nouveau pod est une nouvelle ligne; l'ancien reste.

Ce que prouve cette étape

Les deux sources sont lues: IN = OUT.

Limites

  • La porte voit ce que le hub a lu: le pipeline lance la lecture du cluster juste avant la porte.
  • La version est le tag de l'image. Une image poussée sous un tag déjà approuvé n'est pas détectée: comparer le digest demanderait une autre colonne.
  • Un conteneur par pod est lu (le premier).
  • Cluster kind de démonstration, images construites pour le rejeu.

DevOps · mise en production

Un hotfix part en production sans validation.

Le pipeline doit le voir.

Cluster kind de démonstration

Le problème

Deux vérités, deux endroits.

  • Les versions approuvées: un fichier du comité.
  • Les versions qui tournent: le cluster.
  • Personne ne compare les deux avant de livrer.

Ce qui n'est pas modifié

lumnik lit, il ne touche à rien.

  • Un compte de service qui ne peut que lister les pods.
  • Le CSV reste où il est.

Ce qu'il a fallu écrire

path: /api/v1/pods?labelSelector=…
joins:
  - table: t_approved_versions

Une lecture, une jointure.

4 fichiers, 72 lignes, et une porte shell de 18 lignes.

Le rouge

billing-api: 2.4.0-hotfix, approuvée 2.3.7.

  • La porte sort en 1.
  • Le pipeline s'arrête.
  • La violation nomme le service et son astreinte.

Le vert

Rollback: la même commande repasse.

  • Le hub garde chaque pod vu.
  • La porte lit le plus récent.

La limite

La porte voit ce que le hub a lu.

  • Un hotfix posé après la dernière lecture n'est pas encore vu.
  • Le pipeline lance la lecture juste avant la porte.
